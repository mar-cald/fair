Depositare su Zenodo

Le scelte da fare durante il deposito

Parole chiave: caricare upload zip cartella intera; resource type dataset software tipo risorsa; GitHub DOI release concept versione badge sync integrazione automatica; bozza reviewer secret link peer review revisione anonima; community collaborare coautori insieme; correzioni nuove versioni aggiornare modificare errata.

Il tipo di risorsa

Il campo Resource type è obbligatorio e incide sulla reperibilità: alcuni sistemi di ricerca indicizzano da Zenodo solo pubblicazioni, dataset e software. Per un’intera cartella di progetto Zenodo indica due strade:

  • un solo record, con il tipo che descrive il contributo principale: di solito Dataset, quando gli script servono solo a elaborare i dati. Per conservare la struttura del progetto (data/, scripts/, output/) si carica un unico file .zip, di cui Zenodo mostra il contenuto nell’anteprima. Prima di caricarlo, aprite lo zip e controllate che contenga solo i file del progetto (alcuni sistemi operativi aggiungono file nascosti).

  • più record, uno per tipo, quando dati e codice sono ciascuno un contributo a sé: un record Dataset per i dati e uno Software per il codice, collegati fra loro nel campo Related works.

Licenza e copyright

Il campo Copyright serve a dichiarare chi detiene i diritti, mentre la License dice che cosa possono farne gli altri.

Il campo License è obbligatorio e di default è impostato su CC BY 4.0: se per i dati avete scelto CC0, va cambiato. Nello stesso record si possono indicare più licenze, per esempio CC0 per i dati e MIT per il codice.

Il campo Copyright si compila con una riga come “© 2026 Nome Cognome”, o con il nome dell’ente quando i diritti appartengono all’università o a un editore.

Condividere una bozza prima di pubblicare

Una bozza su Zenodo non è pubblica e si può modificare fino alla pubblicazione. Si può però condividere, per esempio con i revisori di una rivista:

  1. Salvate la bozza con i metadati minimi: il pulsante Share si attiva solo dopo.
  2. Cliccate Share e aprite la scheda Links.
  3. Create un link con il permesso Can preview draft. Il permesso Can view non va bene, perché vale solo per i record già pubblicati.
  4. Se serve, impostate una data di scadenza del link.

Il link funziona anche per chi non ha un account Zenodo, e non rivela a nessuno chi lo apre (documentazione).

Double-blind peer-review

Il link protegge l’identità di chi revisiona, non la vostra: l’anteprima mostra la pagina del record come sarà pubblicata, autori compresi. Se i revisori non devono sapere chi siete, sostituite gli autori della bozza con “anonymous” e togliete i riferimenti a voi dal contenuto dei file (README, intestazioni degli script, percorsi come /Users/nome/...). Prima di pubblicare, rimettete i nomi.

Lavorare in più persone

Sulla stessa bozza. Con Share si può condividere la bozza con un altro utente Zenodo. Con il permesso Can edit può compilare i metadati e aggiungere file insieme a voi.

Su un intero progetto: le community. Una community è uno spazio che raccoglie i record di un progetto o di un laboratorio (o altro). Può avere membri con ruoli diversi (Reader, Curator, Manager, Owner).

Correzioni e nuove versioni

  • Entro 30 giorni dalla pubblicazione si possono modificare i file in autonomia, dall’interfaccia, mantenendo lo stesso DOI e senza creare una nuova versione.
  • Dopo i 30 giorni la modifica diretta è ammessa solo in casi giustificati (per esempio una violazione di copyright o dati personali esposti) e su richiesta motivata; per tutto il resto si pubblica una nuova versione.
  • I metadati (titolo, autori, descrizione, licenza) si correggono in qualsiasi momento con il pulsante Edit, senza creare una nuova versione.

Ogni nuova versione riceve un proprio DOI, mentre il concept DOI continua a rimandare alla più recente.

Da GitHub a Zenodo

Se il codice o l’intero progetto sta su GitHub, Zenodo può archiviarlo da solo.

  1. In Zenodo, dal menu del profilo si apre GitHub e si collega l’account (comodo se ci si è iscritti con ORCID).
  2. Si preme Sync e si attiva l’interruttore accanto il repository. Deve essere pubblico su GitHub, i repository privati non compaiono.
  3. Su GitHub si crea una release con un tag di versione (per convenzione v1.0.0).
  4. Zenodo archivia quella release e le assegna un DOI. Ogni release successiva riceve un DOI proprio, mentre un concept DOI unico rimanda sempre all’ultima versione (nell’articolo si cita quello).

Testo adattato da Johnson, E. (2026). Linking GitHub to Zenodo — generating DOIs and adding to communities. Zenodo. 10.5281/zenodo.20428659, che mostra ogni passaggio con le schermate.
